# CloudSense AI — Persistent Workspace Rules

## Project identity
- This is an EXISTING repository. Inspect before editing; prefer targeted changes to rewrites.
- Product goal: CloudSense AI — cloud cost management, forecasting, optimization, and CarbonSense sustainability analytics.
- Known stack: Next.js 15 + React 19 + TypeScript frontend; FastAPI + Pydantic + SQLAlchemy backend; PostgreSQL / SQLite fallback; Scikit-learn & NumPy analytics.
- Preserve the current frontend stack. Do not replace frameworks without a documented reason and explicit approval.

## Safety and change control
- Run `git status --short` before changes. Never discard uncommitted user work.
- Use a dedicated phase branch when appropriate. Do not commit or push unless requested.
- Ask for approval before destructive actions, deleting files, changing public API contracts, adding dependencies, migrating real data, or contacting cloud/provider services.
- Use the project virtual environment. Never install dependencies globally.
- Do not run destructive SQL, reset Git, or overwrite source files blindly.
- Do not print, log, or commit secrets. Keep `.env` git-ignored and use placeholders in `.env.example`.

## Correctness and honesty
- Never fabricate production data, provider connections, forecasts, accuracy, savings, emissions, test outcomes, screenshots, or deployment status.
- Demo data must be isolated, clearly labelled, and never blended with real customer data.
- Report only commands/tests actually run, with their actual outcomes.
- If data, credentials, provider access, or methodology is missing, state the limitation and implement only the supportable portion.
- Do not mark a feature complete merely because its page, route, or file exists.

## Engineering
- Inspect the actual routes, schema, dependencies, frontend, and data model before changing them.
- Validate inputs at boundaries. Use parameterized SQL/ORM parameters. Do not execute arbitrary SQL generated by the AI assistant.
- Enforce authorization server-side on every protected route and isolate workspace data.
- Use Decimal or integer minor units for money where practical; never rely on binary floating-point for authoritative currency arithmetic.
- Store event timestamps consistently and define reporting time zones explicitly.
- Handle currencies and units explicitly; never add unlike currencies or emissions units without a documented conversion.
- Prevent duplicate imports with stable record identities and/or idempotency handling.
- Keep cost totals consistent across APIs, dashboard, exports, and reports.

## Forecasting and anomaly detection
- Use chronological time-series splits and avoid future-data leakage.
- Compare forecasts with a reasonable baseline and report real MAE/RMSE plus suitable percentage metrics where meaningful.
- Never promise a fixed forecast accuracy.
- Store model version, evaluation window, relevant metrics, and artifact identity where feasible.
- Label insufficient-data results clearly.
- Anomaly alerts must preserve observed value, baseline, deviation, rule/model version, and trigger explanation.

## CarbonSense
- Each emissions figure must include a source or documented methodology, unit, reporting period, and reported/estimated/demo status.
- Never calculate reliable cloud emissions from spend alone.
- Only calculate an estimate when required energy/usage data and defensible emission factors exist.
- Preserve factor source, geography, year/validity period, units, and version.
- Do not claim certification, audit, or regulatory compliance without evidence.

## AI analyst and recommendations
- Use allowlisted backend functions to query data. No generated arbitrary SQL or shell commands from user messages.
- Ground answers in authorized application data; state when information is unavailable.
- Recommendations must show evidence, assumptions, trade-offs, and estimates separately from verified outcomes.
- Simulations must not mutate live cloud resources.
- Do not make production changes to cloud infrastructure without explicit, informed user authorization.

## Testing and documentation
- Every behavior change needs an appropriate test or an explicit explanation of why testing is blocked.
- Run relevant tests, lint/format checks where configured, and build checks where applicable.
- Update `docs/PROJECT_STATUS.md`, relevant API/schema docs, and ADRs when decisions warrant them.
- Report exact files changed, commands run, test results, known gaps, and how to verify the feature.
- Do not claim browser verification unless the browser was actually used; do not fabricate screenshots.
